# Cuelor Provider API v1

- Status: the text of version 1.0.0. It is final once `spec-v1.0.0` is tagged.
- This document is the normative text of the protocol. Schemas: [`schemas/`](schemas/) (JSON Schema
  draft 2020-12) are the source of truth for every shape below. [`openapi.yaml`](openapi.yaml) describes
  the same endpoints for tooling.
- Local plugins (handshake, manifest, recovery): [`plugins.md`](plugins.md).
- Conformance tests: [`../conformance/README.md`](../conformance/README.md).
- Changes per version: [`CHANGELOG.md`](CHANGELOG.md).
- Section numbers follow the design this text comes from, so there are no sections 2 and 4.
- Requirements marked *(not checked by the conformance suite)* cannot be tested from outside the service;
  passing the suite does not show that they are met.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be read as described in RFC 2119. Field
names and error codes are English `snake_case`.

## 1. Overview

Cuelor generates images and video and transcribes speech only through this protocol. A provider is an
HTTP service that speaks it. There are three kinds, and the client treats them the same way:

| Kind | Who runs it | Authentication |
|---|---|---|
| The official service (`cuelor`) | Cuelor's cloud | The account token from signing in |
| A local plugin | The Cuelor app starts it as a command; it listens on `127.0.0.1` only | A random token the app generates each time it starts the plugin |
| A self-hosted service | The user, at a URL they enter | A token the user enters |

v1 covers what the client needs today: the catalog, uploading and downloading artifacts, jobs (submit,
query, cancel), transcription, estimates and usage. It does not cover streaming output, batch jobs,
listing all jobs, fine-tuning or picking the best of several results. Voice-over (text to speech) is not
part of the protocol. Later additions follow the rules in section 3.11.

**Division of work.**

- The client chooses the model and route, checks parameters and inputs against the catalog, freezes the
  request, creates the idempotency key, polls with backoff, decides whether a replay is safe, downloads and
  verifies outputs, and records where each result came from.
- The service translates the protocol to its upstream API, remembers idempotency keys, reports status,
  cost and moderation results, and keeps artifacts until the client has downloaded them.
- Third-party keys stay inside the plugin or the self-hosted service. The client never stores or sees them.

**Polling is authoritative.** Webhooks are an optional capability that the Cuelor app does not use
(section 3.5.6).

## 3. Protocol

The protocol sections keep the numbers 3.1 to 3.11 of the design they come from, so a reference such as
"section 3.5.2" means the same thing in Cuelor's documents, in the conformance suite and here.

### 3.1 Transport, authentication and versions

- **HTTP and JSON.** Requests and responses are UTF-8 JSON, except uploads and downloads. Remote services
  MUST use HTTPS. Local plugins use plain HTTP on `127.0.0.1` only.
- **Path prefix `/v1`.** The major version is in the path. Within a major version there are only
  backward-compatible additions (section 3.11).
- **Authentication.** Every request carries `Authorization: Bearer <token>`. Section 1 lists where the
  token comes from. The service MUST compare it in constant time and MUST NOT write it to logs *(not
  checked by the conformance suite)*.
- **Version negotiation.** The client sends `Cuelor-Protocol: 1.<minor>` with every request: the minor
  version it implements, for information only. The service reports the version it implements as
  `protocol.version` in `GET /v1/provider`. The client does not use a service whose major version is
  not 1. The minor version is only a hint; what a service can do is in `capabilities`.
- **Unknown fields.** Both sides MUST ignore fields they do not recognise.
- **Response time.** Apart from uploads and downloads, the service SHOULD respond within 10 seconds and
  MUST respond within 30 seconds (the client's request timeout). When the upstream API is synchronous
  (for example synchronous image generation or transcription), the service MUST accept the job, return
  `queued` or `running` at once, and call the upstream in the background.
- **Rate limits.** The service MAY return 429 with `Retry-After`. The client treats it as a temporary
  error (section 3.8).

### 3.2 Provider description: `GET /v1/provider`

The client reads it after starting a plugin, when it first uses a service, and when the settings page
opens. Schema: [`provider-description.json`](schemas/provider-description.json).

```json
{
  "protocol": { "version": "1.0" },
  "provider": {
    "id": "example.images",
    "name": "Example Images",
    "version": "0.3.1",
    "repository": "https://example.com/example-images"
  },
  "capabilities": {
    "generation": ["image", "video"],
    "transcription": true,
    "cancel": true,
    "estimate": true,
    "webhook": false,
    "setup": true
  },
  "account": {
    "status": "ready",
    "label": "Example key …a1b2",
    "binding": "6f1c…(64 hexadecimal digits)"
  },
  "billing": { "unit": "USD" }
}
```

- `provider.id` MUST equal the `id` in the plugin manifest ([`plugins.md`](plugins.md)), whose syntax
  the manifest defines. A self-hosted service has no manifest; its id is any non-empty string. The
  official service is `cuelor`.
- `capabilities`: a missing boolean means `false`; a missing `generation` means the service generates
  nothing. With `setup`, the service offers `POST /v1/setup`, which returns `{url, expires_at}`
  ([`setup.json`](schemas/setup.json)): a page the host opens for the user to set the upstream key, and
  when it stops working ([`plugins.md`](plugins.md), section 5). `webhook` stays an optional capability;
  the Cuelor app does not use it (section 3.5.6).
- `account.status`: `ready` (usable), `needs_setup` (no upstream key or login yet),
  `invalid_credentials` (the upstream rejected the current key). When it is not `ready`, the catalog and
  job endpoints return 403 `provider_not_ready` (section 3.8). This applies to new work: the catalog,
  estimates, new submissions and cancelling a job that has not ended. What the service already knows is
  still answered, from its own storage and without calling the upstream: a submission that replays a key
  it has recorded returns that job (section 3.5.2), and `GET /v1/jobs/{id}` returns a job it created.
  The rule of section 3.5.2, that a submission is answered with 4xx only when the service is certain that
  no job was created, takes precedence over this 403: when the service cannot tell which account a
  submission belongs to (it cannot derive the `binding`), it returns 503 `upstream_unavailable` with
  reason `binding_unavailable`, a temporary error.
- `account.label`: an account description for people. MAY be omitted. MUST NOT contain the full key
  *(not checked by the conformance suite)*.
- `account.warnings` (MAY): `[{code, message}]`, account-level things the user should know. Agreed code:
  `non_commercial` (the upstream account's current plan does not allow commercial use of outputs, or
  requires attribution when publishing). Services MAY use other codes. The client shows them in settings
  and before generating with this service; it does not block on them.
- `account.binding`: **a stable fingerprint of the upstream account or credentials**, 64 hexadecimal
  digits. It MUST NOT allow the key to be recovered. When it changes *(not checked by the conformance
  suite)*:
  - It MUST change when the upstream account changes.
  - It MUST change when the key changes, **unless** the service, under the new key, still finds the jobs
    it created under the old key and still recognises their idempotency records (section 3.5.2): its
    jobs and idempotency records belong to the account, not to the key.

  The reason: the client records the binding with each job it submits. While the binding stays the
  same, the client goes on querying those jobs and replays a submission whose result is unknown with the
  **same** `Idempotency-Key`, whatever key the service now uses. A service that did not recognise the
  earlier records would answer 404, so the client loses the job, or create a second job and charge
  again. When the binding differs, the client pauses the job instead of replaying it: an upstream's
  idempotency scope is usually "account + key", so replaying under another account creates a second job
  and a second charge.

  For example: generate a random salt when the plugin is installed and report HMAC-SHA256(salt, key),
  which changes with every key. A service that keeps its jobs and idempotency records itself, and can
  still reach the upstream jobs with a new key of the same account, MAY report HMAC-SHA256(salt, account
  id) instead, so a new key does not pause the jobs. `binding` is present in every `status`. A service
  that has no credential yet derives it from an empty one (with the first example, HMAC-SHA256(salt,
  "")), so it still changes when a credential is set.
- `billing.unit`: `credits` (the official service) or an ISO 4217 currency code (a plugin reporting the
  upstream's money).

### 3.3 Catalog: `GET /v1/models`

Schema: [`catalog.json`](schemas/catalog.json).

```json
{
  "models": [{
    "id": "example/video-1",
    "label": "Example Video 1",
    "provider": "Example Labs",
    "description": "Prompt references are passed to the upstream as an ordered list.",
    "available": true,
    "output": { "modality": "video" },
    "parameters": [
      { "name": "prompt", "kind": "text", "required": true, "max_length": 2000 },
      { "name": "duration", "kind": "integer", "default": 5, "min": 4, "max": 15, "step": 1, "unit": "s", "widget": "slider" },
      { "name": "ratio", "kind": "enum", "default": "16:9", "enum_values": ["16:9", "9:16", "1:1"] },
      { "name": "video_resolution", "kind": "enum", "default": "720p", "enum_values": ["480p", "720p"] },
      { "name": "audio", "kind": "boolean", "default": true },
      { "name": "audio_prompt", "kind": "text", "max_length": 500, "label": "Sound", "visible_when": { "name": "audio", "equals": true } }
    ],
    "parameter_rules": [
      { "when_name": "ratio", "when_values": ["1:1"], "reject_name": "video_resolution", "reject_values": ["480p"], "message": "480p is not available in 1:1" }
    ],
    "routes": [{
      "id": "multimodal2video",
      "label": "Multimodal to video",
      "input": {
        "slots": [
          { "id": "reference", "role": "reference", "modality": "image", "min_artifacts": 0, "max_artifacts": 9, "media_types": ["image/png", "image/jpeg"], "max_bytes": 31457280 },
          { "id": "video_track", "role": "video_track", "modality": "video", "min_artifacts": 0, "max_artifacts": 3, "media_types": ["video/mp4"], "max_duration_ms": 15000 },
          { "id": "audio_track", "role": "audio_track", "modality": "audio", "min_artifacts": 0, "max_artifacts": 3, "media_types": ["audio/mpeg", "audio/wav"] }
        ],
        "max_total_artifacts": 12
      },
      "parameter_names": ["prompt", "duration", "ratio", "video_resolution", "audio", "audio_prompt"],
      "output": { "media_types": ["video/mp4"], "audio": "optional" },
      "pricing": { "basis": "estimate", "unit": "second", "amount": 0.12, "currency": "USD", "note": "720p; audio included" }
    }]
  }]
}
```

**Model.**

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique within one service. MAY contain `/`. The client tells models apart by (service id, model id): the same upstream model offered by two services is two models. |
| `label` | yes | Display name. |
| `provider` | no | Who makes the model, for display. |
| `description` | no | Free text. |
| `available` | yes | Whether the model can be used now. |
| `availability_reason` | no | Why it is not available, for display. |
| `output.modality` | yes | `image`, `video`, or `text` for transcription models (whose routes output `application/vnd.cuelor.transcript+json`). |
| `parameters[]` | yes | Parameter definitions (below). |
| `parameter_rules[]` | no | Rules that combine parameters (below). |
| `routes[]` | yes | Ways to call the model (below). |

**Route.**

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Route id (table below). |
| `label`, `description` | no | Display text. `description` SHOULD explain how prompt references are translated (section 3.6). |
| `input.slots[]` | yes | Input slots (below). Empty when the route takes no inputs. |
| `input.max_total_artifacts` | no | Upper bound for the number of inputs across all slots. |
| `input.modality` | no | Informational. |
| `parameter_names[]` | yes | The model parameters that apply to this route. |
| `output.media_types[]` | no | The possible output types. |
| `output.audio` | no | Sound of a video route: `none`, `always`, or `optional` (decided by the `audio` parameter). |
| `pricing` | no | A price hint (below). |

**Slot.**

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | Unique within the route. |
| `role` | yes | The role an input in this slot has, for example `reference`. |
| `modality` | yes | `image`, `video` or `audio`. |
| `min_artifacts`, `max_artifacts` | yes | How many inputs the slot takes. |
| `media_types[]` | yes | Accepted MIME types. |
| `max_bytes` | no | Upper bound for the size of one input. |
| `max_duration_ms` | no | Upper bound for the duration of one audio or video input. |

The client checks all of these locally before submitting: model available, route exists, number and MIME
type of the inputs per role, the total, `max_bytes`, `max_duration_ms`, parameter types and ranges.

**Parameter.**

| Field | Required | Meaning |
|---|---|---|
| `name` | yes | Unique within the model. |
| `kind` | yes | `text`, `string`, `number`, `integer`, `boolean` or `enum`. |
| `required` | no | Whether the request must set it. |
| `default` | no | MUST be inside `enum_values` and inside `min`..`max`, and aligned with `step`. A request that leaves the parameter out means the `default`; the service applies it. |
| `enum_values` | for `enum` | Allowed values. A `number` or `integer` parameter MAY list its allowed values here as well, as numbers of its kind (for example `duration` with `[4, 6, 8]`); a value is then one of them. Clients MUST support this. |
| `min`, `max`, `step` | no | Range for numbers; values are `min + k * step` for a whole number `k` (from 0 when there is no `min`). `min` ≤ `max`, `step` > 0. `step` MAY be fractional for a `number` parameter (for example `0.5`). `max` does not have to be aligned. Because of floating-point rounding, alignment is compared with a small tolerance. |
| `unit` | no | Display unit, for example `s`. |
| `label` | no | Display name. |
| `max_length` | no | Maximum number of characters of a `text` parameter. |
| `widget` | no | A string: a display hint, for example `slider`. v1 does not fix its values; clients ignore hints they do not know. |
| `visible_when` | no | `{name, equals}`, both required: a display condition. The parameter is shown while the parameter `name` has the value `equals` (any JSON value, `null` included). |

**Parameter rules.** Each item of `parameter_rules` is `{when_name, when_values, reject_name,
reject_values, message}`; all five are required. While the parameter `when_name` has one of
`when_values`, the parameter `reject_name` MUST NOT have one of `reject_values`. `message` explains the
rule in English, for people. `when_name` and `reject_name` are strings, `when_values` and
`reject_values` arrays of strings.

`widget`, `visible_when` and `parameter_rules` are optional; when present they MUST have these shapes.
Later minor versions extend them only in backward-compatible ways (section 3.11).

**Routes.** v1 defines these routes. A service MAY list others; the client does not use routes it does
not know and shows the model as incompatible, with the reason.

| Route | Inputs | Output | Used by the Cuelor app |
|---|---|---|---|
| `text2image` | none | image | yes |
| `image2image` | ordered `reference` images | image | yes |
| `text2video` | none | video | yes |
| `image2video` | one `first_frame` image, the first frame of the video | video | yes |
| `frames2video` | one `first_frame` and one `last_frame` | video | not yet |
| `multiframe2video` | ordered key frames `frame` | video | not yet |
| `multimodal2video` | `reference`, `video_track`, `audio_track` mixed, ordered | video | yes |
| `audio2text` | one `audio` | transcript | yes |

In `image2video` the image is the first frame. A video guided by reference images that are not frames
is `multimodal2video` with only `reference` images.

v1 has no voice-over route.

**Agreed parameter names.** The client treats these names specially, and services SHOULD use them for the
same meaning. Other parameters are shown generically by their kind.

| Name | Meaning | How the client handles it |
|---|---|---|
| `prompt` | The prompt; may contain input references (section 3.6) | Filled in from the compiled prompt |
| `ratio` | Aspect ratio, for example `16:9` | Defaults to the project's ratio when the model declares it |
| `width`, `height` | Custom size; both or neither | Exclusive with `ratio`; needs `resolution` |
| `resolution`, `video_resolution` | Resolution tier of images and video | Enum |
| `duration` | Video length in seconds | Range and step from the catalog, or the `enum_values` it lists |
| `audio` | Whether a video has sound | Only present when `output.audio` is `optional` |
| `language`, `timestamps` | Transcription parameters | See section 3.7 |

**Price hint (optional).** `pricing` lets the client show an approximate price when choosing a model:
`basis` (`exact` or `estimate`), `unit` (`image`, `second`, `character`, `minute` or `job`), `amount`,
`currency` (`credits` for the official service, otherwise ISO 4217) and `note`. Exact costs come from the
estimate endpoint (section 3.9).

**Caching.** Clients MAY cache the catalog per (service id, binding). The Cuelor app reuses a catalog for
60 seconds, and when refreshing fails with a temporary error it uses one up to 10 minutes old. A service
MAY return `ETag`; v1 clients do not use it.

### 3.4 Artifacts

An artifact is a file the service keeps: an input the client uploaded, or a job's output.
Schema: [`artifact.json`](schemas/artifact.json).

**Upload: `POST /v1/artifacts`** (multipart, field `file`, with a filename and a MIME type)

```json
{ "id": "art_9f2c41", "media_type": "image/png", "bytes": 482113, "sha256": "3a6e…" }
```

- **Deduplicated by content.** Uploading the same bytes with the same type under the same account MUST
  return the same `id`. Replays depend on this: the client uploads again when it replays, and must not get
  different inputs.
- `sha256` MUST be the SHA-256 of the bytes received, in hexadecimal. The client compares it; a mismatch
  counts as a failed upload that can be retried.
- **Size limit.** The upload does not say which slot it is for. When every slot of the catalog declares
  `max_bytes`, the service MUST reject an upload larger than the largest of them with 413
  `payload_too_large` and `params.max_bytes` (that largest value). When some slot has no `max_bytes`,
  uploads have no declared limit.
- **Retention of inputs.** The service SHOULD keep uploaded inputs for at least 30 days, as long as the
  idempotency keys of the submissions that use them (section 3.5.2). A submission or an estimate that
  refers to an artifact the service does not have (never uploaded, or no longer kept) is rejected with
  400 `invalid_request`, reason `artifact_not_found` and `params.artifact_id`. The client then uploads
  the input again (the same bytes get the same `id`) and submits again.
- MIME aliases: the service SHOULD accept common aliases such as `audio/x-wav` and `audio/wave`. Clients
  normalise types before uploading as well.

**Metadata: `GET /v1/artifacts/{id}`**

```json
{ "id": "art_5d0e17", "media_type": "video/mp4", "bytes": 10485760, "sha256": "…",
  "created_at": "2026-10-23T08:00:00Z", "expires_at": "2026-10-30T08:00:00Z",
  "metadata": { "width": 1280, "height": 720, "duration_ms": 5000, "audio": true } }
```

Every `metadata` field is optional: images `width`, `height`; video also `duration_ms`, `audio`; audio
`duration_ms`, `sample_rate`.

**Download: `GET /v1/artifacts/{id}/content`**

- The response MUST have `Content-Type` and `Content-Length`. It MAY support `Range`.
- **Redirects.** The service MAY answer 302 or 307 with a `Location` elsewhere, for example a signed
  address in object storage. That address MUST NOT require the protocol's bearer token and SHOULD stop
  working after a short time. The client:
  - MUST follow such redirects, at most 5 of them;
  - MUST NOT send `Authorization` to another origin (when the scheme, the host or the port differs from
    the service's);
  - MUST NOT follow a redirect from `https` to `http`;
  - MAY refuse a redirect to a loopback or private address, except when the service itself is on one
    (a local plugin).

  The requirements on `Content-Type` and `Content-Length`, and the client's checks of length and
  SHA-256, apply to the **final** response. Only this endpoint may redirect; the client does not follow
  redirects from any other endpoint (section 3.8).
- The client checks the length and SHA-256 after downloading, then identifies the type from the file
  header. A mismatch counts as a failed download that is retried later.
- **Retention.** Output artifacts MUST be kept for at least 7 days after the job succeeded. After they
  expire the service returns 410 `artifact_expired`. The client records the result as expired on its own
  side and does not retry. This is not a job state: the service does not change the job's state, which
  stays `succeeded`.
- A local plugin SHOULD download results into its own data directory as soon as the upstream job ends:
  the upstream's retention may be short, and the plugin does not run while the app is closed.

### 3.5 Jobs

#### 3.5.1 Submit: `POST /v1/jobs`

Schema of the body: [`job-request.json`](schemas/job-request.json).

```http
POST /v1/jobs
Authorization: Bearer …
Idempotency-Key: gen_01JB…
Content-Type: application/json
```

```json
{
  "model": "example/video-1",
  "route": "multimodal2video",
  "input": {
    "artifacts": [
      { "artifact_id": "art_a", "role": "reference", "position": 0 },
      { "artifact_id": "art_b", "role": "video_track", "position": 1 },
      { "artifact_id": "art_c", "role": "reference", "position": 2 }
    ]
  },
  "parameters": { "prompt": "The person in @image1 walks into the street of @video1 and looks back at @image2", "duration": 5, "ratio": "16:9" }
}
```

- `Idempotency-Key` MUST be present: 1 to 128 visible ASCII characters (0x21–0x7E), the same rule as
  Cuelor's own API. A request without it is rejected with 400 `invalid_request`.
- `input.artifacts[].position` numbers the inputs from 0 without gaps. The order is meaningful
  (section 3.6).
- Every `input.artifacts[].artifact_id` MUST name an artifact the service has. Otherwise the answer is
  400 `invalid_request` with reason `artifact_not_found` and `params.artifact_id` (section 3.4).
- A model that is not available (`available: false`) is rejected with 400 `invalid_request` and reason
  `model_unavailable`; an unknown model with reason `unknown_model`.
- The response is 200 or 201 with the job object (section 3.5.3).

#### 3.5.2 Idempotency

- **Scope** is (account, `Idempotency-Key`): under one binding, one key corresponds to one job.
- **Same key, same body: the service MUST return the same job** (same `id`, current state). It does not
  create another job and does not charge again, also when the job has already ended.
- **Same key, different body: the service MUST return 409 `idempotency_conflict`** and create no job.
  "Same body" is compared as JSON values, ignoring key order and whitespace. The client always sends a
  byte-identical body when it replays: the request is generated deterministically from a frozen snapshot.
- **Retention.** Keys MUST be kept for at least 30 days, or until the job is deleted, whichever is longer.
  The client may replay a job whose submission result is unknown long after it was shut down.
- **When the upstream has no idempotency**, the service provides it (for plugins see
  [`plugins.md`](plugins.md), section "Recovery"):
  1. Before calling the upstream, persist "key → submitting".
  2. When the upstream returns its job id, persist "key → upstream id".
  3. On a replay, a key with an upstream id returns that job. A key with only a "submitting" record and no
     upstream id (the service crashed between steps 1 and 2) SHOULD be looked up in whatever way the
     upstream allows (for example by listing recent jobs with custom metadata the request carried). When
     it cannot be found the service MUST return the job as `failed` with `error.code = submission_unknown`
     and MUST NOT submit to the upstream again.

  **`submission_unknown`** means: it is unknown whether the upstream ran the job and charged for it, and
  its result is not available. Besides the case above it covers a synchronous upstream call (section
  3.1) that was cut off while it ran, for example because the service stopped: the upstream may have
  run and charged it, but the result is lost. The agreed reason for that case is `interrupted`.

  The client handles `submission_unknown`: it tells the user the upstream may already have accepted and
  charged the job, and submits again only after the user accepts a possible duplicate charge.
- **How the client classifies submission failures** (services MUST cooperate):

  | Service response | Client behaviour |
  |---|---|
  | 2xx with a valid job object | Records the job id and starts polling |
  | 4xx | Rejected; not replayed. A service MUST return 4xx only when it is certain that no job was created and that submitting the same request again cannot succeed |
  | 5xx, 429, connection failure, interrupted response, invalid body | Result unknown; replayed with the same key after a backoff |

  So when the upstream times out, returns 5xx, or the plugin is not sure whether the upstream accepted the
  job, the plugin MUST return 5xx (or accept the job and end it later with `submission_unknown`) and MUST
  NOT return 4xx.
- **A submission that ends after a 5xx.** When the service answered 5xx while its call to the upstream
  went on, and that call then ends without an upstream job, a replay may already have returned the job's
  `id`. The service MUST keep the job and its key (section 3.5.4) and end the job instead of forgetting
  it. It SHOULD end it like this, with the original HTTP status, `code` and `reason` in `params` as
  `original_status`, `original_code` and `original_reason`:

  | The upstream call ended with | The job ends |
  |---|---|
  | Certainly not accepted, a retry may work (for example a refused connection, or 429) | `failed`, `upstream_failed`, reason `not_submitted` |
  | 422 `content_moderated` | `rejected`, `content_moderated`, with `params.stage` and `params.source` (section 3.10) |
  | 402 | `failed`, `insufficient_credits` |
  | 403 | `failed`, the same `code` and `reason` (for example `forbidden` with `region_restricted`) |
  | Any other 4xx | `failed`, `invalid_input` |

  A replay with the same key returns this job. To try again the client submits with a new key; nothing is
  charged twice, because the upstream did not accept the job. Before the service has answered, the rules
  above apply unchanged: it forgets the key and answers 4xx, or 5xx for a retry.

#### 3.5.3 The job object and its states

Schema: [`job.json`](schemas/job.json).

```json
{
  "id": "job_7c1a90",
  "status": "succeeded",
  "model": "example/video-1",
  "route": "multimodal2video",
  "created_at": "2026-10-23T08:00:00Z",
  "updated_at": "2026-10-23T08:01:12Z",
  "progress": { "percent": 100 },
  "approval": null,
  "outputs": [
    { "artifact_id": "art_out", "role": "output", "media_type": "video/mp4", "bytes": 10485760, "sha256": "…",
      "metadata": { "width": 1280, "height": 720, "duration_ms": 5000, "audio": true } }
  ],
  "error": null,
  "usage": { "amount": 0.6, "unit": "USD", "basis": "billed" }
}
```

**The set of states is closed in v1**; no state will be added.

| State | Terminal | Meaning |
|---|---|---|
| `queued` | no | Accepted, waiting |
| `running` | no | Being generated |
| `pending_approval` | no | Waiting for a person to approve (for example a team budget or an expensive job). `approval` is `{policy, deadline}` |
| `succeeded` | yes | Done; `outputs` has at least one item |
| `failed` | yes | Failed; `error` says why. With `error.code = submission_unknown` the client knows that it is unknown whether the upstream ran and charged the job, that no result will come, and that the upstream side has ended |
| `rejected` | yes | Rejected by an approver or by content moderation; submitting the same request again will not succeed (section 3.10) |
| `expired` | yes | The approval expired |
| `cancelled` | yes | Cancelled (section 3.5.5) |

**Allowed transitions:**

```text
queued ──> running ──> succeeded
  │  ↘        │
  │   pending_approval ──> queued | rejected | expired | cancelled
  └──────────┴──> failed | rejected | cancelled
```

- `running` MAY go to `pending_approval` (an upstream that asks for approval after it started), and a
  job in `pending_approval` MAY be cancelled.
- Polling can miss intermediate states, so a client may see any transition along a path of the diagram
  (for example `queued -> succeeded`).
- A terminal state MUST NOT change again. `updated_at` MUST NOT decrease.
- `outputs` is present only for `succeeded`; other states have no `outputs`, `null` or `[]`. `role` is `output` (images, video) or `transcript` (a
  transcription). In v1 a generation route MUST have exactly one `output` and a transcription exactly one
  `transcript`. When the upstream returns several results for one request, the service keeps the first
  and drops the others; a model that always returns several is not listed.
- `progress.percent` MAY be provided, for display only.
- `warnings` (MAY): `[{code, message}]`, things the user should know about a job that runs normally.
  Agreed codes: `prompt_rewritten` (the upstream rewrote the prompt, for example an automatic prompt fix),
  `model_substituted` (the upstream used an equivalent model), `parameter_ignored` (the upstream ignored a
  parameter, for example an unsupported reference video). Services SHOULD turn such behaviour off; when
  they cannot, they MUST report it *(not checked by the conformance suite)*. The client shows warnings
  with the job and in the result's provenance.
- `approval`: `{policy, deadline}` while `pending_approval`, otherwise `null` or absent. The approver's
  reason for a rejection goes into `error.message`.
- `error`: MUST be present for the terminal states `failed`, `rejected`, `expired` and `cancelled`, in the
  format of section 3.8 (`code`, `message`, optional `reason` and `params`). Agreed job error codes:

  | code | State | Meaning |
  |---|---|---|
  | `upstream_failed` | failed | The upstream reported a failure. Reason `not_submitted`: the upstream did not accept the job, after the service had answered 5xx (section 3.5.2) |
  | `timed_out` | failed | A time limit of the upstream or the service was reached |
  | `invalid_input` | failed | The upstream found an invalid input only after accepting the job (for example an image that does not decode) |
  | `submission_unknown` | failed | Unknown whether the upstream ran the job and charged for it; its result is not available (section 3.5.2). Reason `interrupted`: a synchronous upstream call was cut off while it ran, and its result was lost |
  | `insufficient_credits` | failed | The balance ran out while running |
  | `forbidden` | failed | The upstream refused the account after the service had answered 5xx; `reason` as in section 3.8 (section 3.5.2) |
  | `content_moderated` | rejected | Rejected by content moderation (section 3.10) |
  | `approval_rejected` | rejected | Rejected by an approver |
  | `approval_expired` | expired | The approval expired |
  | `cancelled` | cancelled | Cancelled |

  Services MAY use other codes. The client shows codes it does not know and acts on the state. A job
  that the upstream rejects without giving a reason ends `rejected` with `content_moderated` and
  `params.inferred = true`, because the service inferred the code (section 3.10).

#### 3.5.4 Query: `GET /v1/jobs/{id}`

- Returns the job object. The Cuelor app polls with an interval that doubles from 1 second to 30 seconds
  and goes back to 1 second when something changes.
- The service MUST NOT return 404 for a job it created that is still within its retention. On 404 the
  client records the job as `failed` with `error.code = job_not_found`, because the service has lost it.
- The service SHOULD respond within 2 seconds and not wait for the upstream for long while answering a
  query.

#### 3.5.5 Cancel: `POST /v1/jobs/{id}/cancel` (optional, `capabilities.cancel`)

- Best effort and idempotent. Returns the job object: `cancelled` when the upstream could cancel it,
  otherwise the state is unchanged.
- The Cuelor app v1 does not call this endpoint yet; it is reserved for later use.

#### 3.5.6 Webhooks (optional, `capabilities.webhook`)

- The submission body MAY carry `"callback": {"url": "https://…", "secret": "…"}`. When the job ends the
  service POSTs the job object to it, with the header `Cuelor-Signature: sha256=<HMAC-SHA256(secret,
  body)>` in hexadecimal. It SHOULD retry failed deliveries for up to 24 hours.
- **The Cuelor app does not use webhooks.** The desktop app listens on `127.0.0.1` only and cannot receive
  callbacks; polling is authoritative. The capability is for server-to-server use, for example a
  self-hosted service forwarding to its own systems.
- Local plugins cannot receive upstream callbacks either, so they poll their upstream.

### 3.6 Ordered inputs and prompt references

**What has to be expressed.** A prompt must be able to point at "the second reference image" or "the
first video". Upstreams write this in different ways; the protocol defines one way, and the service
translates it.

**Rules.**

1. The inputs are the list `input.artifacts`, ordered by `position`. The order itself carries meaning:
   which reference comes first, which frame is first or last.
2. A prompt refers to inputs with **`@image<N>`, `@video<N>`, `@audio<N>`**. N starts at 1 and counts
   **within one media type**, in `position` order. Example: with inputs image, video, image they are
   `@image1`, `@video1`, `@image2`. The media type of an input is the top-level type of its artifact's
   `media_type`.
3. Syntax: `@(image|video|audio)[1-9][0-9]*`, not immediately followed by another digit. Every other `@`
   is plain text.
4. A reference to an input that does not exist (for example `@image3` with two images) MUST be rejected
   with 400, `reason = prompt_reference_out_of_range`.
5. Not every input has to be referenced. Unreferenced reference images are still passed to the upstream,
   in order.
6. The service translates references to the upstream's form: to the upstream's own reference syntax when
   it has one; when the upstream only accepts an ordered list, it removes the markers or replaces them
   with wording such as "image 2". How it translates is an implementation detail of the service and
   SHOULD be described in the model's or route's `description`.

The client generates the request body deterministically, so the same frozen request produces
byte-identical bodies on every replay and the service's idempotency comparison is not affected by how the
client stores prompts internally.

### 3.7 Transcription

Voice-over is not in the protocol; the only speech capability of v1 is transcription.

#### 3.7.1 Route `audio2text`

| Parameter | Required | Meaning |
|---|---|---|
| `language` | no | `auto` (default, detect) or a BCP 47 tag |
| `timestamps` | no | `none`, `segment` or `word`. The default is the catalog parameter's `default`; when the catalog gives none, it is `word`. `word` means per word or per unit: by word for languages with spaces; by character or the recogniser's smallest unit for Chinese, Japanese and similar languages |

- Input: one artifact with `role = audio`. The slot declares limits with `max_bytes`, `max_duration_ms`
  and `media_types`. The Cuelor app uploads 16 kHz mono WAV.
- Output: one result with `role = transcript`, in the format below.
- The Cuelor app requires `timestamps = word` for per-take transcription.

#### 3.7.2 Transcript format: `application/vnd.cuelor.transcript+json`

Schema: [`transcript.json`](schemas/transcript.json).

```json
{
  "schema_version": 1,
  "language": "zh",
  "language_probability": 0.97,
  "unit": "character",
  "text": "今天下雨",
  "segments": [{
    "text": "今天下雨",
    "start_ms": 0,
    "end_ms": 1320,
    "timed_text_units": [
      { "text": "今", "start_ms": 0, "end_ms": 280 },
      { "text": "天", "start_ms": 280, "end_ms": 560 },
      { "text": "下", "start_ms": 600, "end_ms": 900 },
      { "text": "雨", "start_ms": 900, "end_ms": 1320 }
    ]
  }],
  "provider": { "name": "example-asr" }
}
```

- `schema_version` MUST be 1.
- `language`: the detected or requested language as BCP 47 (for example `en`, `zh`; when the upstream
  returns ISO 639-3 such as `eng`, the service converts it). `language_probability` MAY be provided.
- `unit` MUST be present: the actual granularity of `timed_text_units`, `word`, `character` or `token`.
  A service MUST fill it in truthfully and MUST NOT pass whole sentences off as words *(not checked by the
  conformance suite)*.
- `timed_text_units`: integer milliseconds from the start of the audio. Units MUST be ordered by time and
  MUST NOT overlap (each unit's `start_ms` is not earlier than the previous unit's `end_ms`), each unit
  has `start_ms ≤ end_ms`, and no unit ends more than 60 ms after the end of the audio.
- When the upstream's words overlap, the service MUST fix them first (for example move a start to the
  previous unit's end). Spaces, punctuation and sound events (laughter, music) SHOULD be removed and not
  reported as units.
- `segments[].start_ms`, `end_ms` and `speaker` MAY be provided.

**This format is also the import format.** An agent that transcribes with another tool converts the
result to this format before importing it.

### 3.8 Errors

Every 4xx and 5xx response that the service itself produces MUST have the error body, the same as
Cuelor's own API. Schema: [`error.json`](schemas/error.json). A proxy or gateway in front of the service
may answer with an error that does not have it; the client then acts on the class of the HTTP status.

```json
{ "error": { "code": "invalid_request", "message": "route multimodal2video accepts at most 3 video_track inputs",
             "reason": "too_many_inputs", "params": { "role": "video_track", "max": 3, "received": 4 } } }
```

- `code`: the category, from the table below. `message`: English, for people. It MUST NOT contain
  secrets, full upstream URLs or signed parameters, and SHOULD be at most 300 characters (the client
  truncates it). `reason`, `params`: a finer cause and its parameters, MAY be provided.
- The client branches only on the HTTP status and `code`, never on `message`.

| HTTP | code | Meaning | Client behaviour |
|---|---|---|---|
| 400 | `invalid_request` | An invalid parameter, input or reference. `reason` refines it, for example `unknown_model`, `model_unavailable`, `unknown_route`, `too_many_inputs`, `unsupported_media_type`, `prompt_reference_out_of_range`, `unsupported_timestamps`, `artifact_not_found` (with `params.artifact_id`) | Rejected; after `artifact_not_found` the client uploads the input again and submits again (section 3.4) |
| 401 | `unauthorized` | The bearer token is wrong (the token between client and service) | Local plugin: restart it and hand over a new token. Remote: ask the user to sign in again or fix the token. Jobs pause; they do not fail |
| 402 | `insufficient_credits` | Not enough balance (official service) or the upstream's balance ran out | Rejected; suggests topping up |
| 403 | `provider_not_ready` | The upstream key is missing or was rejected (`account.status` is not `ready`) | The service shows "needs setup"; running jobs pause, they do not fail |
| 403 | `forbidden` | The account may not use this model or feature. `reason` can be `plan_required`, `region_restricted`, `account_suspended` | Rejected |
| 404 | `not_found` | The resource in the path does not exist (a job or an artifact). An unknown model in a submission or an estimate is 400 `invalid_request` with reason `unknown_model` | See section 3.5.4 |
| 409 | `idempotency_conflict` | Same key, different body | Rejected (a client bug) |
| 410 | `artifact_expired` | The artifact has expired | The client records the result as expired on its own side; this is not a job state, and the service does not change the job's state |
| 413 | `payload_too_large` | The upload exceeds the limit | Rejected |
| 422 | `content_moderated` | Moderation rejected the job at submission (section 3.10) | Rejected |
| 429 | `rate_limited`, `queue_full` | Rate limited, queue full | Temporary; retried after a backoff, submissions replayed with the same key |
| 500 | `internal_error` | An error in the service itself | Temporary |
| 502, 503, 504 | `upstream_unavailable` | The upstream is unavailable or timed out | Temporary |

Services MAY use codes outside this table; the client acts on the class of the HTTP status.

**Redirects.** Only the download `GET /v1/artifacts/{id}/content` may answer with a redirect, under the
rules of section 3.4. The client does not follow a 3xx from any other endpoint and treats it as an
invalid response (for a submission: result unknown, section 3.5.2).

### 3.9 Estimates and usage

- **Price hints**: `pricing` in the catalog (section 3.3), only for showing an approximate price when
  choosing a model.
- **Estimates: `POST /v1/estimates`** (optional, `capabilities.estimate`; the official service MUST
  support it). The body is the same as for `POST /v1/jobs`, without an idempotency key. It creates no job
  and charges nothing. Schema: [`estimate.json`](schemas/estimate.json).

  ```json
  { "estimate": { "amount": 40, "unit": "credits", "basis": "exact", "note": "5 s, 720p" } }
  ```

  `basis`: `exact` (this request will cost exactly this) or `estimate`. The client shows it when asking
  the user to confirm a paid generation.
- **Usage: `usage` in the job object**, which SHOULD be present when the job has ended: `amount`, `unit`
  (`credits` or a currency code) and `basis` (`billed`: what the upstream or the official service actually
  charged; `estimate`: the plugin's own calculation).
- **How it is used.** The official service reports credits, which are metered only on the server. A
  plugin reports what the upstream says; when the upstream says nothing, it reports its own estimate and
  marks it `estimate`. The client only shows and records usage; it never bills from it. The display names
  the source, for example "about $0.60 (plugin estimate)".

### 3.10 Moderation

- **At submission** (for example the prompt violates a policy): return 422 `content_moderated` and create
  no job.
- **While running or after the output exists**: the job ends `rejected` with
  `error.code = content_moderated`.
- **A filtered output is not a success.** Some upstreams replace a violating image with a black image and
  report success. A service that knows its upstream does this MUST detect it; any other service SHOULD
  detect such replacements in the formats it can decode. A detected replacement ends the job `rejected`
  with `content_moderated` (`params.stage = output`), and the replacement file MUST NOT be returned as an
  output *(not checked by the conformance suite)*.
- `error.params`: `stage` (`input` or `output`; clients MUST accept values they do not know, and later
  versions may add values such as `unknown`); `source` (who blocked it: `service` for the service
  itself, `upstream` for the upstream platform or the model maker); MAY include `category` (for example
  `sexual`, `violence`, `minors`, `public_figure`, `copyright`, or the upstream's own category name,
  truncated to 64 characters).
- When the upstream only gives free text (for example a plain "content policy violation" string), the
  service MAY classify it as `content_moderated` by keywords, but SHOULD add `params.inferred = true`.
- Regional restrictions and suspended accounts are not moderation: use 403 `forbidden` with `reason`
  `region_restricted` or `account_suspended`.
- `error.message`: a reason that can be shown to the user. It MUST NOT contain sensitive content beyond
  the rejected input itself *(not checked by the conformance suite)*.
- An approver's rejection uses `error.code = approval_rejected`, separate from content moderation.
- When the upstream charged for a job that moderation rejected, `usage` reports it truthfully.
- The client shows that the job was rejected, why, and whether to change the prompt. It does not retry
  automatically and does not switch models.

### 3.11 Extension rules

- Within v1 there are only backward-compatible additions: new optional fields, new optional endpoints
  (declared in `capabilities`), and new values in descriptive enumerations (routes, roles, parameter
  kinds, error codes, moderation stages and categories).
- A client that does not know a route, role or parameter kind marks the model incompatible and says why.
  A client that does not know an error code acts on the HTTP status.
- **What cannot change**: the set of job states (section 3.5.3), the idempotency semantics (section
  3.5.2), the meaning and type of existing fields, and the `schema_version: 1` transcript format. Changing
  them needs `/v2`, and clients support both major versions for a while.
- Each minor version has a changelog entry ([`CHANGELOG.md`](CHANGELOG.md)) and its JSON Schemas in this
  repository.

## 5. Conformance

The [conformance suite](../conformance/README.md) keeps the check ids and pass conditions of the
design. Tier A (A1–A9) is free. Tiers B (B1–B11) and C (C1–C2) create real jobs and run only with
`--live` and a cost limit, `--max-cost`, in the service's `billing.unit`.

- **Cost limit.** `--live` without `--max-cost` is a usage error. Before submitting any job, the suite
  estimates the cost of the whole live run once: every job that tiers B and C and A6 would submit, with
  B7's retries counted in full, from `POST /v1/estimates` when the service has it, else from the
  catalog's price hints. **When the estimate exceeds `--max-cost`, or the cost cannot be estimated (no
  estimate endpoint and no usable price hint, or the endpoint fails), no job is submitted and the whole
  run fails.** Every B and C check is then reported as failed and not run: `"not_run": true` in the
  report, and a detail that starts with `not run: ` and gives the estimate, the limit and the unit, or
  why there is no estimate. `not_run` is an added field; the report's shape is otherwise unchanged.
- **A6's valid submission.** A6's last step submits a valid request with a new key, which creates a job.
  It runs only with `--live` and within the cost limit. Without `--live` A6 leaves it out; over the
  limit, or when the cost cannot be estimated, it leaves it out with a warning. A6 judges its other steps
  as usual.
- **A6's out-of-range reference.** A6 references one input more than the request supplies
  (`@image<n + 1>`, so `@image1` for a request without images), which is out of range whatever the route
  accepts.
- **Warnings.** A check that passes but finds a missed SHOULD (A9, B10) has the status `warning`. A
  warning does not fail a run and does not change the exit status; a skipped check (one whose capability
  the service does not declare) does not either.
